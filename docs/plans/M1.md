# M1 — Domain model in Core

**Companion to:** `../roadmap.md`, `../tasks.md`, `../design-decisions.md`, `M0.md`
**Covers:** tasks 1.1–1.26
**Status:** draft — not started. Open questions at the end need answers before step 2.

## Context

M0 proved the machinery on one aggregate: HTTP → command → validation → event → projection,
plus replay, in one transaction. M1 keeps that pipeline unchanged and fills the model out —
workspaces, accounts, categories, the full operation shape, transfers, anchors — so that M2 has
something to import into and M3 has something to count.

The risk in M1 is not difficulty, it is **multiplication**. Whatever shape the operation
aggregate has today gets copied five times. Three places where the M0 shape does not generalise
are known already (below), and they cost minutes now against a five-way refactor later. So M1
starts with a short shape-fixing step before task 1.1.

The second risk is the one `tasks.md` names: validation drifting into handlers. Categories are
where it will try to happen (the move rules in 1.14 need a recursive query, and it is tempting
to run it where the row is written). All of it belongs in `validation/`, called before the
event is appended.

**Done when:** every entity in §4 exists with its invariants enforced at command time, CRUD is
reachable over HTTP, and the rebuild-equality test still passes with all aggregates present —
including a workspace whose categories, accounts, operations, transfers and anchors are all
reconstructed from the event log alone.

## Decisions

### 1. The workspace is a record, not an aggregate

`t_workspaces` is an ordinary table written directly by `WorkspaceFacade` — no events, no
payloads, no `WORKSPACE` aggregate type. The workspace is the tenant boundary, not data inside
the tenant, and treating it as an aggregate made replay circular: `replayWorkspace` would have to
delete and re-create, inside one transaction, the very row that scopes the replay.

**Renames are ordinary `UPDATE`s and no history is kept.** A row cannot be authoritative and
derived at the same time: were renames events, either replay would apply them to a table it does
not own, or they would sit in `t_events` unread by the replay loop — a trap for whoever reads that
loop next. A workspace name has no analytical consumer, and §4.7 already establishes that reports
show current names rather than names as of the period.

Workspace mutations are therefore **not** `Command`s: the command pipeline keeps exactly one
meaning — a command produces events. They still run behind a facade, because that is where M5's
ownership check lands and there should be one such place per entry point, not one per mechanism.

**Lifecycle — four statuses, soft delete:**

| Status | Meaning | Writes | Reads |
|---|---|---|---|
| `NEW` | created, empty; the only state import is permitted from | import only | yes |
| `ACTIVE` | operational | all | yes |
| `ARCHIVED` | kept for reference | none — read-only | yes |
| `DELETED` | withdrawn; terminal | none | no — 404 |

```
NEW ──start empty / import──> ACTIVE <──unarchive── ARCHIVED
 │                              │  └──archive──────>  │
 └──────────────> DELETED <─────┴─────────────────────┘
```

`NEW` replaces the design record's `DRAFT`; the semantics are §4.1.1's unchanged — empty, and the
only state import may target — renamed because `DRAFT` reads oddly beside `ARCHIVED` and
`DELETED`. `NEW → DELETED` is permitted (a workspace created and never imported into is the
common case while the interpreter is being written); `NEW → ARCHIVED` is rejected, since there is
nothing to keep for reference; `DELETED` is terminal — there is no restore.

**Archiving is the recoverable path and deletion is not**, and the two are deliberately
asymmetric in how they are reached. Archive is a prominent action in the main UI; delete is
hidden away in workspace settings, states plainly that it cannot be undone, and requires the
user to type the workspace name to confirm. A user who wants a workspace out of sight is meant
to land on archive, not on delete, without having to read anything.

**The confirmation is a client affordance, not an API precondition.** `DELETE /workspaces/{id}`
takes no confirmation parameter and validates nothing beyond the transition — a caller reaching
the API has already decided, and Core does not model second thoughts. Guarding it in Core was
considered (the CLI at M7 is a second client) and rejected: it would make every non-UI caller
carry a token that exists to slow a human hand down.

**Deletion is soft**, which reverses §4.8's "the only true deletion in the system is deleting an
entire workspace". Anchors (§10.4) are then the *sole* physical deletion anywhere.

Storage is reclaimed by a **scheduled retention job**, not by an admin endpoint: a `DELETED`
workspace is hard-deleted once it has been deleted for longer than a configurable window
(default 30 days). §4.2 expects recreate-after-a-bad-import to be frequent while the interpreter
is being written, so without it the database accumulates dead workspaces that every listing must
filter around — but nothing about that needs a human to press a button.

The job is one `DELETE FROM t_workspaces WHERE id = ?` per expired workspace, because
`workspace_id` carries a real foreign key to `t_workspaces(id)` with `ON DELETE CASCADE` on
`t_events` and every projection. Specifics that matter more than the code:

- **The window is not an undo window.** `DELETED` is terminal, so the data is unreachable from
  the moment it is deleted, whatever is still on disk. The retention window is housekeeping, not
  a grace period, and the UI must not present it as one — `ARCHIVED` is the reversible state.
- **`deleted_at`, not `status_changed_at`**, is the column the job queries: self-documenting,
  indexable, and immune to a later status gaining a transition out of `DELETED`.
- **One transaction per workspace**, so a failure on one does not roll back the sweep, and an
  INFO log line per purge with row counts — unattended deletion that leaves no trace is how you
  end up unable to answer "where did that workspace go".
- **Refuse to run on a non-positive retention.** A misconfigured `PT0S` would purge every
  deleted workspace on the next tick, which is precisely the mistake the window exists to
  prevent.
- Configuration: `fintrace.workspace-retention.{enabled,window,cron}`, disabled in tests except
  the one that tests it. The core is a facade method taking the cutoff as a parameter, so the
  test injects a date rather than mocking a clock or waiting a month. `@Scheduled` cron fires in
  the JVM default zone — pinned by `TZ` in Compose (§6.4), which is exactly the kind of thing
  that shifts silently when it is not pinned.
- Single container on a NAS, so no locking. If a second instance ever runs, this needs
  `FOR UPDATE SKIP LOCKED`; noting it here so the assumption is visible rather than forgotten.

### 2. Status guards every command, not just workspace endpoints

Read-only `ARCHIVED` is a rule about the whole system: it forbids creating an operation, moving a
category, archiving an account. So the check belongs at `CommandFacade`, before dispatch — the
same single place M5's ownership check lands — and not in each handler.

| Status | Commands | Reads | Admin replay |
|---|---|---|---|
| `NEW` | import only (plus the category seed at creation) | yes | yes |
| `ACTIVE` | all | yes | yes |
| `ARCHIVED` | none — 409 | yes | yes |
| `DELETED` | none — 404 | no — 404 | yes |

Admin replay is exempt because it writes no facts: it rebuilds derived rows from a log that is
already closed, which is exactly what an archived workspace can afford.

`DELETED` returns 404 rather than 410 on reads, so a workspace's existence is not disclosed to a
caller who cannot use it — and 404 is what M5's ownership failure will return too, for the same
reason.

### 3. `occurredAt` leaves the base interfaces, but the column stays `NOT NULL`

Today `Command` and `EventPayload` both require `occurredAt`. Create-workspace, rename-account,
move-category and archive-account have no business date; supplying one at the command layer would
be inventing data.

**Split the Kotlin side:** `recordedAt` stays on every command and payload, `occurredAt` moves to a
`TemporalCommand` / `TemporalEventPayload` sub-interface implemented by operations, transfer legs
and anchors only.

**Leave the column alone.** `t_events.occurred_at` stays `NOT NULL`, and the one place that writes
the row falls back to `recorded_at` when the payload carries no business date. For those events the
two genuinely coincide — the same rule §4.6 already states for anchors — so this is a degenerate
case rather than a fabricated value, and it costs no migration, no nullable envelope field and no
null-handling in the row mapper.

Rejected: a nullable column, on the argument that "has no business date" and "business date equals
record time" are different facts. They are, but nothing queries `t_events.occurred_at` — replay
orders by `id`, statistics read the projection — so the distinction has no consumer, while the null
is handled forever by every reader.

### 4. An event applies a projection *change*, not a projection

`EventPayload.asProjection(): Projection` assumes one event yields exactly one row. Three M1
cases break that assumption:

| Case | Needs |
|---|---|
| Cancel an operation (1.17) | the row **removed** |
| Delete an anchor (1.23) | the row **removed** (§10.4 — the sole physical deletion) |
| Create/revise a transfer (1.18) | **two** rows, atomically |

Generalise once, at the start:

```
EventPayload.projectionChange(): ProjectionChange
    Upsert(rows: List<Projection>)      // create or replace, keyed by (workspace_id, id)
    Remove(type, workspaceId, id)

ProjectionApplier.apply(change)         // the ONLY projection writer, routes by row type
```

Handlers and `AdminFacade.replayWorkspace` both call the applier, so online and replay still
cannot drift, and the `when (it) { is OperationProjection -> ... }` in the replay loop stops
growing a branch per aggregate. Payloads stay pure data — they return a change, they never see a
DAO.

`Upsert` rather than `insert` matters: replaying `CREATED` then `REVISED` must land on the same
row, so the projection write is idempotent by construction. That is what keeps the
rebuild-equality test honest as revisions arrive.

### 5. What `CANCELLED` means, per aggregate

Event types stay `CREATED` / `REVISED` / `CANCELLED` (§4.11). The mapping to be applied
consistently:

| Domain action | Event | Projection effect |
|---|---|---|
| Cancel operation / transfer | `CANCELLED` | row(s) removed |
| Delete anchor | `CANCELLED` | row removed |
| Soft-delete category (§4.7) | `CANCELLED` | row stays, `deleted = true` |
| Archive / unarchive account (§4.8) | `REVISED` | row stays, `archived` flips |
| Activate workspace | `REVISED` | row stays, `status = ACTIVE` |

Two rules behind the table. **`CANCELLED` is end of life**, whether the projection expresses that
by dropping the row or by a flag; **`REVISED` is every other state change**, including reversible
flags — archiving is explicitly reversible (§4.8), so it cannot be a cancellation.

**Cancelled operations leave the projection entirely.** §10.2 says a cancelled operation
disappears from listings and statistics completely, and notes that filtering it out of every
query by hand is error-prone — so it is filtered out once, by not being there. History lives in
the event log, which is where history belongs. Categories keep their row because operations still
reference them; nothing references an operation or an anchor.

### 6. A transfer is one event over a `TRANSFER` aggregate

`TransferCreatedV1` carries the full state of **both** legs; `aggregate_type = TRANSFER`,
`aggregate_id = transfer_id`; its `projectionChange()` upserts two `t_operations` rows with a
shared `transfer_id` and each leg's `counterpart_id` pointing at the other.

Rejected: emitting two `OPERATION` events. Replay would then have a window — after the first row,
before the second — in which the pair invariant is violated, and cancel/revise would have to keep
two events in step forever. §4.5 puts the pair's atomicity in the domain layer; one event is the
cheapest way to make it structural.

Consequence to accept: `t_operations` rows can come from two aggregate types. Reads do not care —
that is the point of §10.3 — and `PUT /operations/{id}` on a leg is rejected anyway (1.19), which
is now a trivial check: the row has a `transfer_id`.

### 7. `workspace_id` enforcement (1.6): explicit parameter, plus a test

Every DAO method takes `workspaceId` explicitly (`OperationProjectionDAO` already does), and a
test reflects over the DAO companion SQL constants asserting each `SELECT`/`UPDATE`/`DELETE`
mentions `workspace_id`. Crude, but it fails on the day someone adds a query without it, which is
the only thing that matters.

Rejected: a repository-level guard or Postgres row-level security keyed on a session variable.
RLS is the more interesting thing to learn, but it moves the check into invisible control flow at
exactly the moment the model is growing five new tables, and M5 still has to check *ownership*
above this layer regardless.

### 8. Emptiness is not "no rows" — the seeded-categories trap

1.2 seeds four system categories with the workspace; 1.3 defines `NEW` as empty. Taken naively
these contradict each other: a freshly created workspace has four category rows and would fail
its own emptiness check, so every import would be rejected.

**Definition:** a workspace is empty when it has no accounts, no operations, no anchors and **no
non-system categories** (`system = false`). One function, one query per table carrying
`workspace_id`, so adding an entity type later means adding a line here — and a test that lists
the projection tables and fails if one is not covered, since a silently missed table is the
failure mode §4.2 warns about.

Note it does **not** look at `t_events`: a `NEW` workspace has four category events already, and
the workspace itself has none.

### 9. Archiving is a visibility flag, never an arithmetic one

§4.8 left open what happens when an account with a non-zero balance is archived. Settled:
**archiving is permitted unconditionally, and archived accounts keep counting in every computed
figure.** Archiving changes what is *offered*, never what is *counted*.

Requiring a zero balance first was rejected on two grounds. The importer emits source-deleted
accounts as archived (2.10d, 2.12) and MoneyOK does not empty an account before deleting it, so
the rule would force the importer to synthesize a zeroing operation — fabricated facts at exactly
the boundary where §2 says defects are silent. And "balance is zero" is not a stable property
here: balance is computed as of a date and back-dating is normal (§6), so an account that is zero
at archive time stops being zero the moment a retrospective operation is entered. The invariant
can be checked but not maintained.

Excluding archived accounts from cross-account totals was rejected for a sharper reason: it would
let archiving **rewrite history**. The balance series (3.5) would recompute last year's total
because an account was archived today — the retroactive patching §6.2 exists to eliminate.

The remedy for a closed account still carrying a stale balance is model-native and is not the
flag: **an anchor at zero.** "I checked, it is closed and empty" is an observation (§4.6), the
forgotten withdrawal surfaces as that anchor's unexplained difference instead of being silently
swallowed — which §4.6 makes a hard requirement — and balances before the anchor are untouched,
so the historical series stays correct.

Two consequences:

- **Writes to an archived account are rejected at command time** — as an operation's account, as
  either transfer leg, as an anchor target (§4.8: "not offered on either side"). This is what
  makes archiving meaningful without a precondition. A legitimate back-dated entry into a closed
  account goes unarchive → enter → archive: the flag carries no "archived since" date, and
  inventing one would be a second temporal axis.
- **M3's `/balances/accounts` and `/balances/currencies` need an `includeArchived` parameter**
  for picker-style views (3.2, 3.3). A filter on presentation, never a change to the arithmetic.

### Smaller points, settled

- **Currency** is `char(3)`, the ISO-4217 code, validated at command time against
  `java.util.Currency`. No enum in the schema — the importer skips unknown currencies (2.11) and
  M3's provider has its own supported list.
- **No slug in M1.** §4.1 makes it optional and the UUID is the identity; uniqueness has no scope
  to be unique *within* until owners exist at M5. `name` only.
- **No foreign keys *between* projection tables.** They are derived data: an FK turns replay
  order into a schema-level constraint (categories before operations, parents before children)
  for a guarantee that command-time validation already provides. The exception is
  `workspace_id → t_workspaces(id)`, which every table gets: `t_workspaces` is authoritative
  rather than derived, the FK is a real existence guard, and its `ON DELETE CASCADE` is what
  makes the retention job a single statement.
- **Indexes ship with their tables**, not at 3.1 — §4.14's list is one line per table and costs
  nothing to write while the `CREATE TABLE` is open.
- **Migrations `V0004`+**, four digits (`MigrationNamingTest` enforces it). Roughly: `V0004`
  workspaces, `V0005` accounts, `V0006` categories, `V0007` anchors, `V0008` operations full
  field set. Step 1 adds none.
- **`OperationCreatedV1` is edited in place at 1.16, not superseded by a `V2`.** The rule that a
  payload class is immutable once written (§4.10) protects rows already on disk; there are none
  outside development, and the M0 V1 describes an operation with no account and no category —
  a shape that never existed as a real fact. A permanent V1 that never described anything real is
  bookkeeping, not versioning practice. **The rule is absolute from the first real import (M2)
  onward.** One consequence to act on: any existing development database — the Compose volume
  included — must be dropped, since its stored payloads cannot be read by the edited class.
  Tests are unaffected; Testcontainers starts clean each run.
- **A `PUT` with an unchanged body still appends a `REVISED` event — for now.** Suppressing
  no-op revisions is wanted eventually (§4.4) but not at M1: a log line carrying no information
  is harmless, while wrongly suppressing a real edit is silent data loss, and the API contract
  is identical either way, so the deferral costs nothing. When it arrives it must compare whole
  payloads (`equals` on the data class, `recordedAt` normalised), in one place on the revise
  path — a hand-written field comparison is the version that drops an edit when someone forgets
  to extend it, which is the failure this ordering exists to avoid.
- **Rename payloads to `OperationCreatedV1`** to match `design-decisions.md` and `CLAUDE.md`
  (`CreatedOperationEventPayloadV1` today). The `TYPE` discriminator string `operation.created.v1`
  is what is on disk and does not change, so the Kotlin rename is free — and it is free only
  before five aggregates copy the current name.

### Defects to fix in step 1

- `domain/command/OperationCommand.kt:20,26` — `ReviseOperationCommand` and
  `CancelOperationCommand` both implement `CreateCommand<Unit>`. Copy-paste; the dispatcher routes
  on these markers, and both commands are implemented in 1.17.
- `dao/WorkspaceDAO.kt` — an empty interface and an empty impl with an unused `JdbcClient`.
  Filled by 1.1, deleted otherwise.
- `CreateOperationCommand` has no `accountId`, `categoryId`, `kind` or `comment`; the projection
  has no columns for them. That is 1.16, not an oversight.

## Layout

New packages follow M0's, one file per aggregate rather than one per class:

```
domain/command/         AccountCommand.kt  CategoryCommand.kt  OperationCommand.kt
                        TransferCommand.kt  AnchorCommand.kt   (no WorkspaceCommand)
domain/event/payload/   AccountCreatedV1.kt … one file per payload version, forever
domain/workspace/       Workspace, WorkspaceStatus — a record, deliberately not under projection/
domain/projection/      AccountProjection  CategoryProjection  OperationProjection
                        AnchorProjection
                        ProjectionChange   ProjectionApplier
dao/                    WorkspaceDAO — t_workspaces is authoritative, so not under dao/projection/
dao/projection/         one DAO per projection table
service/command/handler/{account,category,operation,transfer,anchor}/
validation/             one validator per aggregate; CategoryValidationService owns the tree rules
api/v1/controller/      WorkspacesRestController  AccountsRestController
                        CategoriesRestController  OperationsRestController
                        TransfersRestController   AnchorsRestController
```

`ProjectionApplier` lives beside the projections rather than in `dao/` deliberately: it is the
place the "only the event handler writes projections" rule is enforced, and it should be
findable from the domain side.

## Work sequence

### 1. Shape fixes — no task number, before 1.1

Decisions 3, 4 and the payload rename, plus the marker-interface defect. **No migration** — the
`occurredAt` split is Kotlin-only, so the first M1 migration is `V0004` at step 2. Nothing new is
added; the 53 existing tests must stay green, which is exactly what makes this step safe to do
first.

### 2. Workspace — 1.1–1.6

`V0004` creates `t_workspaces(id, name, status, default_currency, recorded_at, deleted_at)` and
adds the `workspace_id` foreign key — `ON DELETE CASCADE` — to `t_events`. `deleted_at` is what
the retention job queries.

`WorkspaceFacade.create` is one transaction: insert the row as `NEW`, then dispatch four
`CreateCategoryCommand`s for the system categories (§4.7) with `system = true`. So the workspace
row is written directly and everything beneath it goes through the command pipeline — the split
from decision 1, visible in the very first method.

Status transitions (1.4) are facade methods with the transition table from decision 1 enforced in
one place: `activate` serves both the "start empty" button and M2's import; `archive` /
`unarchive`; `delete` sets `DELETED`. Rejections are 409, and an already-`ACTIVE` activate is a
rejection, not a no-op — it means the caller believed something false about the workspace.

The decision-2 guard is wired here too, in `CommandFacade`: it needs the workspace status, so it
needs `WorkspaceDAO`, and every subsequent step inherits the check for free.

The retention job (decision 1) also lands here — trivial while only `t_workspaces` and `t_events`
exist, and every table added afterwards is covered automatically by the cascade rather than by
remembering to extend it.

1.6 is the DAO convention plus its test, applied to everything written from here on.

**Done when:** create → `NEW` with four categories, activate → `ACTIVE`, activate again →
rejected, archive → every command 409s while `GET` still works, delete → invisible to reads,
delete → invisible to reads and `deleted_at` set;
retention job with an injected cutoff → no rows anywhere for that id.

### 3. Accounts — 1.7, 1.8, 1.10

`V0005` `t_accounts(name, currency, icon, archived)`. Create / rename / archive / unarchive.
`DELETE /accounts/{id}` archives (§10.1). Opening balance (1.9) waits for anchors.

Archive carries no precondition and every later write validates against the flag (decision 9):
the archived-account rejection is added here and re-checked by operations (step 5), transfers
(step 7) and anchors (step 6) as each arrives.

Accounts come second on purpose: it is the smallest aggregate that exercises `REVISED` and the
reversible-flag rule, so decisions 4 and 5 get tested before four more aggregates depend on them.

### 4. Categories — 1.11–1.15

`V0006` `t_categories(name, icon, parent_id, kind, deleted, system)`. The tree rules (1.14) are
the densest validation in M1 and all of it is command-time: same-branch moves only, target is not
a descendant of the node being moved, `Others` stays a leaf, `system` rows reject every mutation.

1.12's recursive descendants query is written once as a reusable component here, because 1.14 and
M3's 3.8 are the same query — that is the entire reason it is a separate task.

**Done when:** a cross-branch move, a move into own descendant, a child under `Others`, and a
rename of a system category are each rejected before any event is written — assert on the event
count, not just the HTTP status.

### 5. Operations, full shape — 1.16, 1.17

`V0008` adds `kind`, `account_id`, `category_id`, `transfer_id`, `counterpart_id`, `comment`,
`external_ref` (§4.13). `amount` stays signed. Revise and cancel commands land here, cancel
removing the row per decision 5.

Validation: the account exists and is not archived, the category exists and is not deleted, the
category's branch matches `kind`, `INCOME` amounts positive and `EXPENSE` negative. A `null`
category resolves to the branch's `Others` (2.14 depends on this).

### 6. Anchors — 1.21, 1.22, 1.23, then 1.9

`V0007` `t_anchors(account_id, value, occurred_at, recorded_at)`. Create rejects back-dating —
`occurred_at` is set by the server, not the client (§4.6: the count happened now). Delete is
permitted only for the account's latest anchor and removes the row (§10.4).

1.9 closes here: an account's opening balance is a `CreateAnchor` in the create-account
transaction, not a column — the second multi-event command, and worth confirming it still
replays identically.

### 7. Transfers — 1.18, 1.19, 1.20

One aggregate, one event, two rows (decision 6). `POST`/`PUT`/`DELETE /transfers`; legs remain
readable through `/operations`; `PUT /operations/{id}` on a row with a `transfer_id` returns 409
(1.19). Cross-currency legs carry their own amounts in their own accounts' currencies — the
importer will produce these, so do not assume the amounts match.

### 8. Balances — 1.24, 1.25, 1.26

Query only, no new events: nearest preceding anchor + `SUM(amount)` after it (§4.6), the
unexplained difference for an anchor, and "confirm balance" as an ordinary anchor created at the
currently computed value. Read paths live in `ProjectionFacade`, not in a handler.

This is the seam where M3 begins; keep the SQL in the anchor/operation DAOs rather than inventing
a statistics layer now.

## Verification

1. `./gradlew clean test` green — `clean`, per `CLAUDE.md`.
2. **The rebuild-equality test extended to every aggregate:** build a workspace with categories,
   accounts, operations, a transfer, anchors, a cancelled operation and a deleted anchor; snapshot
   all five projection tables; wipe them; replay; assert identical. The cancelled operation and
   the deleted anchor must be *absent* after replay — that is the test that proves decision 4 is
   implemented and not merely intended.
3. Status guard: with the workspace `ARCHIVED`, one command of each aggregate type is rejected
   and `t_events` does not grow; with it `DELETED`, reads 404. Assert this at the facade, so a
   handler added later cannot quietly escape it.
4. The retention job, given a cutoff, removes every row for that id from `t_events` and all five
   projection tables — and leaves a workspace deleted more recently than the cutoff untouched.
   A second test asserts it refuses to run with a non-positive window.
5. Emptiness: a fresh `NEW` workspace is empty; one account makes it non-empty; the four system
   categories never make it non-empty.
6. Every rejection in step 4 asserts `t_events` did not grow.
7. `curl` walk-through: create workspace → account → category → operation → transfer → anchor →
   read balances, end to end against Compose.

## Open questions

None outstanding — every question this plan raised has been answered and folded into the
decisions above. The one deferred item is no-op revision suppression (§4.4), which changes no
API contract and can land any time after the write path settles.

## Amendments to `design-decisions.md` — applied

The design record is the authority (`CLAUDE.md`), so these belong there rather than only here,
and they were applied on 2026-09-02/03, before any M1 code. Reversals are marked in place with a
**Revised at M1** note rather than silently rewritten: the record's value is the rationale it
carries, and "decided, then revised, for this reason" is worth more than a clean overwrite.

The same renames were propagated to `CLAUDE.md`, `docs/roadmap.md` and `docs/tasks.md` (tasks
1.4 and 1.5 changed meaning, not just wording; 1.5b and 4.3b are new). Restore
(`DELETED → ACTIVE`) was considered and rejected: archiving is the reversible path.

| Section | Change |
|---|---|
| §4.1.1 | the one-way `DRAFT`/`ACTIVE` lifecycle becomes the four statuses of decision 1; `DRAFT` renamed `NEW`; `ARCHIVED` read-only system-wide; deletion soft and terminal, reclaimed by a retention job; archive-vs-delete UI asymmetry, confirmation is a client affordance |
| §4.2 | "delete and recreate" after a bad import means soft-delete and recreate; emptiness excludes the seeded system categories |
| §4.3 | the handler contract is upsert-or-remove, with the per-aggregate meaning of *cancelled* (decision 5) |
| §4.4 | no-op revisions: appended at M1, suppression deferred, equality must be structural |
| §4.5 | a transfer is one event carrying both legs (decision 6) |
