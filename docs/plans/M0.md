# M0 — Walking skeleton

**Companion to:** `../roadmap.md`, `../tasks.md`, `../design-decisions.md`
**Covers:** tasks 0.1–0.13
**Status:** complete — tasks 0.1–0.13 done. Next milestone: M1 (`docs/tasks.md`).

## Context

`fintrace` is a rewrite of the MoneyOK Telegram bot (`~/projects/moneyok-analyzer-telegram-bot`)
as a small distributed system.

M0 builds one operation end to end — HTTP → command → event → projection → HTTP — plus the
full-rebuild procedure. It is deliberately thin: no import, no statistics, no UI. The point is to
get the event-sourcing machinery working *as a whole* rather than as parts, and to establish the
invariants every later milestone depends on.

The rebuild belongs here rather than later for a specific reason (`design-decisions.md` §4.10):
written after the fact, it usually turns out handlers were not idempotent and a stray direct write
happened somewhere, at which point replay is impossible and ES has degenerated into an audit log
with extra steps.

**Done when:** operations can be created over HTTP, the projection can be wiped and rebuilt from
events, and the result is identical.

## Decisions

Settled with the user:

| Decision | Choice |
|---|---|
| Migrations | **Flyway**, plain versioned SQL |
| Build layout | **Standalone Gradle build per service** — own wrapper, own settings, versions pinned per service |
| Toolchain | **JDK 25 + Spring Boot 4.1.1**, Kotlin 2.4.0 |

Following from the design record and existing conventions:

- **Group / package `com.github.melancholic.fintrace`**.
- **Spring JDBC (`JdbcClient`), not JPA.** §4.10 requires that *nothing* writes to a projection
  except the event handler; JPA's dirty checking and entity lifecycle actively work against that
  invariant, and would make a stray flush hard to see. Statistics (M3) are recursive SQL anyway.
  Postgres is fixed, so JPA's portability buys nothing here.
- **Money is `numeric(19,4)` / `BigDecimal`, never `Double`.** The old bot uses `Double` throughout
  (`StatisticsProvider.kt`); this is the moment to not inherit that.
- **`timestamp`, not `timestamptz`.** §6.4: timestamps are stored in the system timezone with no
  zone attached. Kotlin side is `LocalDateTime` — matching §6.5, which forbids converting source
  timestamps to UTC without an explicit user-supplied zone.
- **`TZ=Europe/Nicosia`** pinned explicitly on both containers (host zone; §6.4 requires it be a
  deliberate choice, not a container default).
- **Projection tables carry no write-time-generated values** — no `bigserial` PK, no
  `DEFAULT now()`. Every column comes from the event. This is precisely what makes the
  rebuild-equality test (0.12) meaningful rather than vacuous.
- **Migrations are named `V0001__`, four digits, always.** Flyway compares versions numerically,
  so `V1`, `V01` and `V0001` are all version 1 — mixing widths fails at startup with
  `Found more than one migration with version 1`. Pick the width once and never vary it.

### One conflict in the docs, resolved

Task 0.6 says "UUIDv7 generation — native `uuidv7()` if on PG 18, otherwise pick a library", but
§4.12 says the id is *generated in code, travels inside the event, and a rebuild reproduces exactly
the same ids*. §4.12 wins — a database-side default cannot satisfy it, since a rebuild would mint
fresh ids and break every inter-entity reference stored in earlier events.

So: **UUIDv7 generated in application code** via `com.fasterxml.uuid:java-uuid-generator:5.1.0`,
behind a `UUIDGenerator` interface so tests can substitute deterministic ids. JDK 25's
`java.util.UUID` still has no v7 factory. Column type is `uuid`. Postgres 18 is still the right
image, just not the id source.

The implementation uses `Generators.timeBasedEpochRandomGenerator()` rather than the monotonic
`timeBasedEpochGenerator()`: it keeps no shared counter and so is safe to call from any thread,
and millisecond-granular ordering is all the index locality UUIDv7 is here for.

## Layout

```
fintrace-core/
  settings.gradle.kts  build.gradle.kts  gradlew
  src/main/kotlin/com/github/melancholic/fintrace/core/
    domain/command/       Command hierarchy — Create/Revise/Cancel, per aggregate
    domain/event/         Event envelope, EntityType, EventType
    domain/event/payload/ EventPayload hierarchy — one file per payload version
    domain/projection/    projection row models
    facade/               CommandFacade — the entry point and transaction boundary
    service/command/      CommandDispatcher + per-command handlers
    dao/                  EventsDAO, projection DAOs — the only SQL
    validation/           command-time invariants
    util/                 UUIDGenerator, TimestampProvider
    api/v1/               controllers, DTOs, MapStruct mappers
    security/             IdentityProvider — the single auth slot
    exception/            domain exceptions mapped to HTTP status
  src/main/resources/db/migration/   V0001__baseline.sql, V0002__events.sql, V0003__operations.sql
  src/test/kotlin/...
deploy/
  docker-compose.yml    Dockerfile
```

`deploy/` mirrors the old bot's shape (`deploy/common/Dockerfile`); the snapshot/production split
there is a CI concern and waits for M6.

## Work sequence

### 1. Project skeleton — tasks 0.1, 0.3 ✅

Gradle Kotlin DSL, `kotlin("jvm")` + `plugin.spring` 2.4.0, Boot 4.1.1, JDK 25 toolchain.
Dependencies: `spring-boot-starter-web`, `spring-boot-starter-jdbc`, `flyway-core`,
`flyway-database-postgresql`, `postgresql`, `jackson-module-kotlin`, `java-uuid-generator`;
test: `spring-boot-starter-test`, `spring-boot-testcontainers`, `testcontainers:postgresql`.

`V0001__baseline.sql` is an empty baseline so Flyway owns the schema from the first migration.

### 2. Schema — tasks 0.4, 0.5 ✅

`V0002__events.sql` creates `t_events` per §4.11 — `id bigint GENERATED ALWAYS AS IDENTITY` PK
(global ordering, drives rebuild; the database alone assigns it), `workspace_id`,
`aggregate_type`, `aggregate_id`, `event_type`, `payload jsonb`, `occurred_at`, `recorded_at`;
index `idx_t_events_workspace_id_id`.

`V0003__operations.sql` creates `t_operations` — the minimal projection: `id uuid` PK (the aggregate id, from the event),
`workspace_id`, signed `amount numeric(19,4)`, `occurred_at`, `recorded_at`. Signed amount so
balance is `SUM(amount)` with no `CASE` (§4.13). The full field set arrives at 1.16.

No `workspaces` table yet (that is task 1.1), so `workspace_id` is an unconstrained `uuid` at M0.

### 3. Event envelope — tasks 0.6, 0.7 ✅

`Event` (envelope, mirrors the table) and a sealed `EventPayload` hierarchy carrying `version`,
`id`, `occurredAt` and `recordedAt`, serialised to `jsonb` via Jackson with a versioned type
discriminator (`operation.created.v1`). `CreatedOperationEventPayloadV1` holds the **full
resulting state**, never a delta (§4.4).

Because the envelope derives `entityId` and `recordedAt` from the payload, the two cannot
disagree — there is no second place for a caller to pass them.

Round-trip tests use Boot's configured `ObjectMapper`, since that is the one that writes `jsonb`.

### 4. The single write path — task 0.8 ✅

Built as a command pipeline rather than a single service method, so every later command copies
the shape:

```
CommandFacade.processCommand(command)     // @Transactional — the one boundary
  └─ CommandDispatcher                    // routes by Command type
       └─ CreateOperationCommandHandler
            ├─ validate(command)          // ALL invariants, before the event (§4.10)
            ├─ EventsDAO.registerEvent()  // INSERT ... RETURNING id
            └─ OperationProjectionDAO     // the ONLY projection writer
```

Commands are a sealed hierarchy typed by result (`CreateCommand : Command<UUID>`, revise and
cancel `Command<Unit>`), and every command carries `workspaceId` — which is what will let the
facade check ownership uniformly once M5 arrives.

Validating inside a handler after the append is too late — the event has already happened and
cannot be rejected. `tasks.md` names this as the predicted drift.

Deliberately deferred here: workspace-ownership enforcement and the facade/dispatcher split that
would make the check unskippable. Both wait for controllers (0.9) and Spring Security.

### 5. HTTP surface — task 0.9 ✅

`POST /api/v1/workspaces/{workspaceId}/operations` → 201 with the new id and a `Location` header
built from the controller's own mapping; `GET .../operations/{operationId}` → the projection via
a MapStruct mapper. Conventional REST — event sourcing does not leak into the API (§10.0).

`workspaceId` is taken from the path only, never the body, so the two cannot disagree. A missing
operation — including one requested under the wrong workspace — raises `NotFoundEntityException`
rather than surfacing a data-access error.

**Known gaps:** CSRF is still enabled, so every `POST` requires a token — that suits a browser
session, not the token-authenticated BFF and CLI this API is actually for. And workspace
*ownership* is still unchecked: any authenticated caller may read or write any workspace. Both
belong with M5, and ownership is planned as a custom annotation rather than inline checks.

The list endpoint (`GET .../operations`) is not built; only fetch-by-id.

### 6. Identity slot — task 0.10 ✅

`IdentityProvider` (interface + injectable `IdentityProviderImpl`) in `security/`, reading the
principal from Spring Security's `SecurityContextHolder`. **One** place, because the CLI (M7)
arrives as a second client and M5 replaces exactly this. Nothing else may resolve identity.

`SpringSecurityConfiguration` carries a minimal filter chain — everything authenticated except a
permitted list. No authentication *source* yet: Keycloak, OIDC discovery and JWT validation are
M5 (§7.4). Ownership enforcement is deliberately deferred to when controllers exist, and will be
applied via a custom annotation rather than inline checks.

### 7. Rebuild — task 0.11 ✅

`AdminFacade.replayWorkspace(workspaceId)`: clear the projection for that workspace, load its
events `ORDER BY id`, and apply each one. The mapping is `EventPayload.asProjection()` — the very
method the command handler uses, so online and replay cannot drift (§4.10).

Replay applies **stored events**; it never travels the command path, which would validate and
append new events, corrupting the log it is rebuilding from.

Reading events back needs a hand-written `RowMapper`: the `payload` column is `jsonb` and the two
type columns are `text`, neither of which `SimplePropertyRowMapper` can convert.

Exposed at `POST /admin/api/v1/workspaces/{workspaceId}/replay`, gated on the `ADMIN` role —
earlier than task 7.5 anticipated, and worth it given the endpoint wipes a whole projection.

### 8. Tests — tasks 0.12, 0.13 ✅

Testcontainers `postgres:18` with `@ServiceConnection`. The rebuild-equality test creates N
operations, snapshots `operations`, replays, and asserts the rows are identical — meaningful only
because of the no-write-time-values rule above.

The stronger companion: delete every projection row, replay, and assert they return. That proves
the projection is derivable from the log alone rather than merely self-consistent. Plus: replay
appends no events, is idempotent, and is scoped to one workspace.

### 9. Compose — task 0.2 ✅

`postgres:18` + `fintrace-core`, `TZ=Europe/Nicosia` on **both**, healthcheck on Postgres, Core
waiting on it. Dockerfile `FROM eclipse-temurin:25-jre`.

## Verification

1. `cd fintrace-core && ./gradlew test` — round-trip and rebuild-equality tests green against a
   real Postgres via Testcontainers.
2. `docker compose -f deploy/docker-compose.yml up --build` — stack starts, Flyway migrations apply.
3. `curl -X POST localhost:8080/workspaces/<uuid>/operations -d '{...}'` then `GET` the same path —
   the operation comes back.
4. `docker compose exec postgres psql -c "select now()"` — confirms the pinned zone took effect.
5. Wipe and rebuild inside the test, asserting identity — the actual definition of done.
